## Acquisition sequence and implementation gates

1. Establish reference access and fixture permissions. Use dedicated synthetic sketches/reports that cover straight and curved geometry, area classification, dimensions, labels, symbols, owned imagery, subject metadata, calculations, multiple pages, units and rounding. Preserve originals and operate on copies. Keep private customer files and licensing data outside distributable fixtures.
2. Capture native identities before conversion. Use the existing [fixture capture](../apex-fixture-evidence.md) tooling to record hashes and bounded header fingerprints; its `native_format=unknown` and `compatibility_passed=false` are deliberate. Record producer executable identity, edition/modules/settings and observed save/open/import/export operations. Include corrupt/truncated and unsupported-version copies as failure fixtures.
3. Resolve native schema lawfully from permitted documentation and representative bytes. Record known signatures/version discriminators, length bounds, object/field semantics, units, curves, resource ownership and unknown-field preservation. Compare Open, Import-into-current, Save As, native Base64 serialization and image export separately. Do not infer native bytes from an extension, image, generated Vertex project, or type-library methods. If the vendor interface is the available observation route, keep it in the reference environment; Vertex's independent native parser still needs representable data and preservation evidence.
4. Implement the parser as a detached bounded import candidate, with no document mutation while parsing. Validate all geometry/references/resources before a single reviewed import operation. Reject unknown versions/invalid data without changing the destination. Preserve unsupported native content or explicitly report loss; a printable image is not preservation of native geometry. Native export needs declared version grammar and a consumer reopen fixture before the target can be qualified.
5. Observe one exact caller exchange. Capture actual arguments or interface calls, native payload versus rendered output, subject/area mappings, return/event ordering, cancellation, errors, timeout/crash, offline behavior and host persistence. Determine page-index origin, export-options grammar, activation registration and process bitness by observation. Installer ProgIDs/dependencies now provide concrete probes; they do not authorize activation or certify behavior.
6. Build an application-specific worker and capability descriptor from that observation. Keep it independent of drawing internals and reuse the existing preparation transport. Native caller return/commit requires a separately designed transaction and reconciliation path: the preparation dispatcher cannot perform or authorize host writes, retries, or delayed writes after timeout/cancellation/uncertainty.
7. Acquire and exercise the selected DISTO interface/device. Translate observed unit/value/error data into the existing version-1 reading envelope, using explicit field selection and retained model/firmware/transport/provenance. Define reading ID/replay policy, disconnect/reconnect, stale-reading rejection, device-unit changes and deliberate replacement. Keyboard-emulated numeric input alone cannot establish device identity, original units and provenance.
8. Qualify per exact matrix row using field-by-field fidelity and real native/consumer/caller/device outcomes. Include timeout, cancellation, offline and crash fixtures. The [compatibility evidence schema](../apex-compatibility-matrix.md) records supplied observations and hashes; complete manifests still do not certify compatibility. Change ledger status only after root reviews actual implementation and the recorded outcomes.

## Existing seams and gaps

`IntegrationAdapterRegistry` owns immutable descriptors and selects by domain, operation, format identity and compatible same-major versions; duplicate IDs, ambiguous requests, unsupported versions and cross-owner-thread access fail closed. It is a capability registry, not parser/device execution. Register only implemented versioned capabilities with provenance and license metadata.

`field_adapter_contract.hpp` supplies strict local JSON DTOs: exact protocol 1.0, explicit selected DISTO target, original unit and provenance, occupied-field rejection, and one-way appraisal text mapping with exact application/version/format identity. Required/optional mappings and numeric/unit interpretation must come from observed host behavior. The future device session owns replay detection across destinations.

`AppraisalDispatcher` provides exact negotiation, correlated preparation acknowledgement, one absolute deadline, cancellation and typed terminal failures. [WindowsAppraisalBoundary](../appraisal-native-transport.md) already provides a trusted-local opt-in no-window worker launcher, bounded framed IPC, minimized environment/handles and Job Object cleanup. It runs under the caller's Windows token; it is not a filesystem/network/credential sandbox. Reuse it rather than duplicating transport. Vendor worker implementation, restricted-token deployment where required, vendor error translation, host commit/reconciliation and actual compatibility fixtures remain open.

At this inspection, the transport section in [field-adapter-contracts.md](../field-adapter-contracts.md) said no native subprocess launcher was supplied; that statement predates the current opt-in Windows transport. The root owns correcting that stale description. Use the current transport source and dedicated transport document for this prerequisite.
